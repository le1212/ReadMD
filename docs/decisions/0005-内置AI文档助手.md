# 决策：内置 AI 文档助手（Agent）

- 日期：2026-10-21
- 状态：已采纳（v0.4.0 实施）

## 背景

用户希望 ReadMD 内置一个 AI Agent：

- 用户自己配置模型，支持国内和国外服务商；
- 用户输入需求，Agent 理解后直接帮助完成文档相关的任务；
- 支持图片识别、复制粘贴图片、上传图片；
- 支持上传并识别文档（PDF、Word 等）；
- 尽量让非技术用户也能用起来。

这不是一个“小功能”，而是会改变产品定位的大功能。需要先明确边界：

1. **文档 AI 助手**：读写当前 Markdown、选区改写、跨文件检索、图片/文档理解、生成修改建议。
2. **通用自主 Agent**：可以执行任意命令、改代码、操作系统的 Agent。

本决策建议先做 **1**，不要在一期做 **2**。原因：

- ReadMD 是本地 Markdown 编辑器，用户的核心诉求是“把文档写好”，不是让 AI 接管电脑；
- 通用 Agent 需要 shell 权限、进程管理、权限沙箱和更高的安全成本；
- 文档助手可以用“修改建议 + 用户确认”的方式落地，风险可控、价值直接；
- 未来如果需要通用能力，可以通过 MCP/外部 Agent 接入，而不是把 ReadMD 变成一个高风险的操作系统 Agent。

### 已完成的最小验证

以下验证在当前仓库、Node 24 / Electron 42（内置 Node 24.15.0）上实际跑通：

1. **AI SDK 流式输出**：用本地 mock OpenAI 兼容服务，`streamText` 正常收到逐字输出。
2. **工具调用循环**：mock 返回 `tool_call`，AI SDK 执行工具、把 `tool_result` 回传、继续第二轮模型调用并返回文本；`propose_edit` 这类“提出修改”工具可用。
3. **图片消息**：AI SDK 把图片内容转换成 OpenAI `image_url` 数据 URL；当前 v7 会提示 `image` part 已弃用，实施时应使用带 `mediaType` 的 `file` part。
4. **Electron 主进程集成**：主进程用动态 `import()` 加载 AI SDK，并通过 `net.fetch` 发请求，流式输出正常；这意味着可以沿用 Electron 的系统代理设置，也无需放开渲染进程 CSP。
5. **密钥加密**：Windows 上 `safeStorage.isEncryptionAvailable() === true`，加密/解密 round-trip 正常。
6. **PDF 文本提取**：`unpdf.extractText` 从 A4 PDF 中提取到标题和正文（也会带出页脚文字）。
7. **DOCX 文本提取**：用 JSZip 读取 `word/document.xml`，从导出的 DOCX 中提取到完整正文。

| LM Studio | OpenAI 兼容 | 取决于模型 | 取决于模型 | 本地/离线 |

结论：**不能假设所有模型都同时支持“工具调用 + 流式 + 图片”**。必须在模型配置里显式标记能力，并在能力不足时降级：

- 不支持工具：走“文本输出完整 Markdown/补丁”的兼容模式；
- 不支持流式但有工具：改为非流式工具调用（例如 Qwen 的 tools 与 stream 冲突）；
- 不支持图片：提示用户切换视觉模型，或仅处理文字。

## 决策

### 1. 产品范围

一期做 **内置“文档 AI 助手”**：

- 聊天式交互；
- 自动附带当前文档/选区作为上下文；
- 可以搜索、读取当前文件夹内的 Markdown；
- 生成修改建议，**必须用户确认后才写入文档**；
- 支持图片（视觉模型）和文档上传（PDF/DOCX/TXT/MD）；
- 支持用户配置多个模型服务商，切换使用；
- 不做 shell、不做任意命令执行、不自动改文件、不做全自动多步任务。

### 2. 技术架构

```text
Renderer（sandboxed）                     Main process
┌─────────────────────────┐   IPC        ┌─────────────────────────────┐
│ AI 面板（原生 JS）       │ ───────────► │ Provider 配置 / 密钥解密     │
│ 聊天消息 / 附件 / diff   │ ◄─────────── │ AI SDK streamText + tools    │
│ 当前文档 / 选区          │   stream     │ net.fetch（系统代理）        │
└─────────────────────────┘              │ 文件搜索 / 读取 / 文档解析   │
                                         └─────────────────────────────┘
```

- **API Key 只存在主进程**：用 `safeStorage` 加密后写入应用状态；渲染进程只能看到“已保存/未保存”，永远拿不到明文 Key。
- **网络请求只在主进程**：渲染进程 CSP 保持 `connect-src` 不放开；主进程用 `net.fetch` 走系统代理。
- **AI SDK**：主进程动态 `import()` 加载 `ai`、`@ai-sdk/openai`、`@ai-sdk/openai-compatible`、`@ai-sdk/anthropic`、`@ai-sdk/google`。OpenAI 用原生适配，其他 OpenAI 兼容服务用 `openai-compatible`。
- **文档上下文**：渲染进程把当前文档/选区/附件文本随请求发送；主进程负责拼 system prompt 和调用模型。
- **工具**：搜索/读文件/提出修改建议在主进程或渲染进程执行，所有写操作都返回“建议”，不直接落盘。
- **流式输出**：主进程通过 `webContents.send` 把 `text-delta`、`tool-call`、`tool-result`、`finish` 事件发给渲染进程。
- **取消**：主进程保存 `AbortController`，渲染进程“停止生成”时调用 `ai:abort`。

### 3. 模型配置

每个配置包含：

```json
{
  "id": "deepseek",
  "name": "DeepSeek",
  "type": "openai-compatible",
  "baseURL": "https://api.deepseek.com/v1",
  "model": "deepseek-chat",
  "apiKeyEnc": "safeStorage 加密后的 base64",
  "supportsTools": true,
  "supportsVision": false,
  "supportsStreaming": true,
  "maxContextChars": 32000
}
```

- 预设：OpenAI、Anthropic、Gemini、DeepSeek、Kimi、智谱、Qwen、SiliconFlow、OpenRouter、Ollama、LM Studio、自定义 OpenAI 兼容；
- 地址和模型名都可编辑，避免服务商改名/改地址后预设失效；
- “测试连接”发一条极小请求，返回成功/失败和延迟；
- 能力开关由用户确认，UI 不猜测；
- 多配置可保存、切换；每个会话可以选不同模型；
- 如果 `safeStorage` 不可用，Key 只保存在内存中，并明确提示“关闭应用后需要重新输入”，绝不写明文。

### 4. Agent 工具与修改确认

一期的工具集：

| 工具 | 作用 | 是否写文件 |
| --- | --- | --- |
| `search_files` | 在当前打开的文件夹内搜索 Markdown 文本，返回文件路径和片段 | 否 |
| `read_file` | 读取当前文件夹内的某个 Markdown/文本文件，限制大小 | 否 |
| `propose_edit` | 提出“原文 → 修改后”的局部修改建议 | 否 |
| `propose_document` | 提出整篇文档的新版本 | 否 |
| `propose_create_file` | 提出新建 Markdown 文件（路径 + 内容） | 否 |

- 所有 `propose_*` 只返回建议，不写文件；
- UI 用行级 diff 展示，用户点“应用修改”后才调用编辑器的替换操作；
- 应用后提供“撤销本次应用”，保存修改前的内容；
- 如果 `oldText` 在当前文档中找不到或不唯一，拒绝自动应用，提示用户重新选择；
- 不允许 shell、任意网络请求、读取文件夹外文件；
- 系统提示明确要求模型把文档内容当作数据，不执行文档里的指令（防提示注入）。

### 5. 多模态

**图片**

- 聊天输入框支持粘贴、拖拽、选择图片；
- 发送前在渲染进程用 canvas 缩放/压缩（例如最长边 2048px），降低 token 和费用；
- 只有标记了“支持图片”的模型才允许发送图片；否则明确提示切换模型；
- 图片以 base64 data URL 发送；AI SDK 负责转成各家的图片格式。

**文档**

- 支持 PDF、DOCX、TXT、MD；
- 主进程本地解析，只把提取出的文本发给模型，不上传原文件；
- PDF 用 `unpdf`，DOCX 用 JSZip 读取 OOXML 正文；
- 显示“已提取 N 字”，发送前可预览/移除；
- 扫描版 PDF 没有文本层时提示“可能是扫描件”，一期不内置 OCR；可让用户上传截图/页面图片，用视觉模型识别；
- 单文件限制 10MB、提取文本限制 10 万字；超出时提示用户截取或分段。

### 6. UI

- 顶部命令栏增加“AI”按钮，打开右侧 AI 面板；
- 右侧面板与大纲共用空间，用标签切换“大纲 / AI”，避免界面过挤；
- 聊天区：消息列表、流式文本、工具执行状态、修改建议卡片、附件缩略图；
- 输入区：多行输入、图片/文档按钮、发送/停止、当前模型选择；
- 设置：模型列表、添加/编辑、测试连接、隐私提示；
- 空状态示例：
  - “总结当前文档”
  - “把选中的段落改写得更简洁”
  - “根据这张图片补一段说明”
  - “把这个 PDF 整理成 Markdown”
  - “在当前文件夹里找一下关于 X 的内容”
- 聊天 UI 用原生 JS + 现有 CSS 设计系统，不引入 React；助手消息最终用 `Vditor.md2html` 渲染 Markdown（带 XSS 过滤），流式过程中先显示纯文本。

### 7. 分期

**一期（建议先做，约 3–4 周）**

- 模型配置（OpenAI 兼容 + Anthropic + Gemini）与加密存储；
- 右侧 AI 面板、流式聊天、停止生成；
- 当前文档/选区上下文；
- 图片粘贴/上传 + 视觉模型；
- PDF/DOCX/TXT/MD 上传解析；
- 局部/整篇修改建议 + diff + 应用/撤销；
- 文件夹搜索/读取；
- mock provider 冒烟测试、打包验证。

**二期**

- 不支持工具/流式的模型降级模式；
- 会话历史、token/费用估算；
- 扫描件 OCR（Tesseract 或视觉模型逐页识别）；
- 文件夹级 RAG/知识库；
- MCP 工具接入；
- 更细的模型预设与能力自动探测。

**三期**

- 多步自主任务、后台任务、可取消/可恢复；
- 自定义 Agent Skills；
- 团队/同步（如确有需求）。

## 影响与风险

- **隐私**：聊天内容和附件会发送到用户选择的模型服务商；必须在设置页明确提示。选择 Ollama/LM Studio 可完全本地。
- **费用**：由用户自己的 API Key 承担；长文档/图片/多轮工具调用会消耗较多 token；一期显示附件字数和估算 token，二期做费用估算。
- **模型能力差异**：国内模型对“工具 + 流式 + 图片”的支持不一致；Qwen 文档明确 tools 与 stream 暂不能同时使用，Ollama 文档称工具/视觉尚未支持。必须做能力开关和降级。
- **提示注入**：上传的文档/图片可能包含恶意指令；系统提示要求把内容当数据，工具受限，写操作需确认。
- **密钥安全**：`safeStorage` 在 Windows 可用；Linux 无可用密钥环时只保存在内存并提示，不落明文。
- **包体积**：AI SDK 约 14MB（未压缩）、unpdf 约 2.5MB、JSZip 约 0.8MB，加上 diff/zod，压缩后预计增加 5–8MB；相对 91MB 的 Electron 包可接受。
- **许可证**：AI SDK/Provider/unpdf/JSZip/zod 为 Apache-2.0/MIT，diff 为 BSD-3-Clause；Cherry Studio/Chatbox/Obsidian Copilot 的 AGPL/GPL 代码不能直接复用，只能参考交互。
- **合规**：产品不内置默认模型服务，不收集数据；用户自行配置服务商和 Key。若面向公众分发并涉及生成式 AI 服务，需按当地法规做合规评估。
- **产品定位**：加入 AI 后，ReadMD 从“本地 Markdown 编辑器”变成“带 AI 的文档工作台”；需要在欢迎页/设置中说明数据流向，避免用户误以为完全离线。

## 验证计划

一期实施时必须包含：

1. 本地 mock OpenAI 兼容服务，覆盖：流式文本、工具调用、图片消息、401/429/超时、取消；
2. 模型配置保存/读取：Key 加密、渲染进程拿不到明文、损坏配置回退；
3. PDF/DOCX 解析夹具：正常文档、空文档、扫描件无文本；
4. 修改建议：diff 渲染、应用、撤销、旧文本找不到/不唯一；
5. 图片：粘贴/拖拽/上传、压缩、非视觉模型提示；
6. UI 冒烟：打开面板、发送、流式、停止、切换模型、清空；
7. 打包后的应用执行同一套冒烟测试；
8. `npm audit --omit=dev` 为 0。

## 实施结果（v0.4.0）

## 备选方案

1. **只做外部 Agent 接入（MCP/Claude Code/Cline）**：不内置模型配置，把 ReadMD 作为工具暴露给外部 Agent；开发量小，但普通用户门槛高，不符合“用户自己配模型”的诉求。
2. **Fork Cherry Studio / Chatbox**：功能最接近，但 AGPL/GPL 传染性不适合 MIT 项目，且会把 ReadMD 变成另一个完整 AI 客户端，偏离 Markdown 编辑器定位。
3. **assistant-ui + React**：聊天 UI 最省事，但需要引入 React 和构建链；当前原生 JS 架构不值得为一个面板改造。
4. **纯本地模型（Ollama）优先**：隐私最好，但工具/视觉能力受本地模型限制，普通用户安装和显存门槛高；作为可选配置，不作为唯一方案。

## 推荐

**按一期实施**：

- 用 Vercel AI SDK + OpenAI 兼容/Anthropic/Gemini Provider；
- 用 `unpdf` + JSZip 做文档解析；
- 用 `safeStorage` 管密钥，主进程用 `net.fetch` 发请求；
- 用原生 JS 做聊天面板，不引入 React；
- 所有文档修改以 diff 建议的形式呈现，用户确认后才写入；
- 一期不做 shell、不做自动落盘、不做扫描件 OCR。

一期完成后，ReadMD 就具备“用户自己配模型、聊天、识图、读文档、改文档”的完整闭环；二期再补降级模式、RAG、OCR 和更复杂的 Agent 能力。
